# セキュリティアドバイザリによる更新 基本設計

> ステータス: 案（2026-10-19）。未実装。採用したら[基本設計](design.md) §14.2 をこの内容で置き換え、実装に必要な決定を[詳細設計](detailed-design.md)に書く。

## 1. 目的

ベースの `pubspec.lock` でロックしているバージョンに、セキュリティアドバイザリ（以下、アドバイザリ）がある場合、それを直すバージョンへの更新を、待機期間（`min_release_age_days`）が過ぎていなくても PR にする。

待機期間は、公開直後のバージョン（壊れたリリースや乗っ取られたリリース）を避けるためのものである。脆弱性の修正は早く入れたいので、この 2 つを両立させるために、待機期間を無視するのは「アドバイザリを直すのに必要な最小限のバージョン」に限る。

## 2. pub と pub.dev のアドバイザリ

- pub.dev は、GitHub Advisory Database のうち Pub のエコシステムのものを、OSV 形式で返す
  - `GET /api/packages/<name>`（バージョン一覧）に `advisoriesUpdated` があれば、そのパッケージにアドバイザリがある。なければない
  - `GET /api/packages/<name>/advisories` が、`advisories`（OSV の配列）と `advisoriesUpdated` を返す
- 影響を受けるバージョンは、`affected[]` のうち `package.name` がそのパッケージで `package.ecosystem` が `Pub` の要素の、`versions` にすべて並ぶ。pub もこのフィールドだけを使い、`ranges` は読まない
- pub は、利用者がルートの `pubspec.yaml` の `ignored_advisories` に書いた ID（アドバイザリの `id` か `aliases` のどれか）のアドバイザリを報告しない
- 取り下げられたアドバイザリ（`withdrawn` がある）も、pub.dev は返す。pub は `withdrawn` を見ていない

## 3. 用語

- **有効なアドバイザリ**: `withdrawn` がなく、ベースの `pubspec.yaml` の `ignored_advisories` に `id` も `aliases` も書かれていないアドバイザリ
- **影響を受けるバージョン**: 有効なアドバイザリのどれかの `affected[].versions` に入っているバージョン
- **要修正のパッケージ**: ベースの lockfile でロックしているバージョン `c(p)` が影響を受けるバージョンである、pub.dev のパッケージ p。直接依存か推移的依存かは問わない
- **修正版 `f(p)`**: p のバージョンのうち、`c(p)` より新しい安定版で、取り下げ（retracted）されておらず、影響を受けないもので、最も古いバージョン（バージョンの順序で最も小さいもの。公開日時の順ではない）

## 4. 中継サーバーで見せるバージョン

待機期間と同じく、中継サーバー（RegistryProxy。基本 §4.2）で pub に見せるバージョンを変える。pub の解決はそのまま使う。

要修正のパッケージ p について、次の 2 つを行う。ほかのパッケージは今までどおり扱う。

1. **影響を受けるバージョンを隠す**: p の影響を受けるバージョンを隠す。ただし、ロック済みのバージョン `c(p)` は今までどおり残す
2. **修正版を見せる**: `f(p)` が待機期間の中にあれば、`f(p)` だけを見せる。`f(p)` が依存するパッケージには、今までどおり待機期間を適用する
3. `ignore` の設定は、これより優先する。`f(p)` が `ignore` に該当するなら見せない

1 は、2 を正しく働かせるために要る。たとえば `c(p)` = 1.2.3 が影響を受け、1.3.0（待機期間の外、影響を受ける）と 1.2.4（待機期間の中、修正版）がある場合、1 がないと pub は今の制約の中で最も新しい 1.3.0 を選び、脆弱性は直らない。

要修正でないパッケージでは、影響を受けるバージョンを隠さない。隠すと、影響を受けるバージョンを要求する依存がある場合に、今まで作れていた PR が作れなくなるため。そのため、要修正でないパッケージの更新先が、影響を受けるバージョンになることはある（そのバージョンが lockfile に入ると、次の実行からは要修正のパッケージとして扱う）。

`f(p)` を「最も新しい修正版」ではなく「最も古い修正版」にするのは、待機期間を無視するバージョンを 1 つにし、公開されてからの時間がなるべく長いものにするためである。修正のバックポート（1.2.4 と 1.3.1 のように、古い系列にも修正が出る）があっても、今の制約に収まる修正版が選ばれる。

## 5. 計画と PR への反映

中継サーバーで見せるバージョンが変わるだけなので、計画（基本 §5）の手順は変えない。

- **要修正の直接依存**: 修正版が今の制約に収まれば、U に入りマイナー・パッチグループに入る。収まらなければ、メジャー更新として単独 PR か同時更新グループに入る
- **要修正の推移的依存**: マイナー・パッチグループの `pub upgrade` で、依存元の制約が許せば修正版に上がる
  - 今は、直接依存が 1 つも変わらなければマイナー・パッチグループを作らない（基本 §5.3）。これを「直接依存か、要修正の推移的依存が変わるなら作る」に変える
  - 依存元の制約が修正版を許さないときは、PR では直さず、ジョブサマリーに出す（§7）

PR がアドバイザリを直すかどうかは、計画ではなく、適用した後の lockfile の差分で判定する（基本 §5.5 と同じ）。要修正のパッケージが、影響を受けないバージョンに変わっていれば、その PR はアドバイザリを直す。

### 5.1 タイトルと本文

- アドバイザリを直す PR のタイトルには、接頭辞 `[Security] ` を付ける（例: `[Security] Update archive from 3.3.7 to 3.3.8`）。接頭辞は固定で、設定では変えられない。コミットメッセージの 1 行目もタイトルと同じにする（基本 §6）
- マイナー・パッチグループの N（基本 §6）には、本文の表に載せた要修正の推移的依存も数える
- 本文の表に、要修正の推移的依存も `transitive` の種類で載せる（ほかの推移的依存は今までどおり載せない）
- 本文の先頭に、直すアドバイザリの表を置く

```markdown
Fixes the following security advisories.

| Package | Advisory | Severity | From | To |
|---|---|---|---|---|
| [archive](https://pub.dev/packages/archive) | [GHSA-9v85-q87q-g4vg](https://github.com/advisories/GHSA-9v85-q87q-g4vg) Path traversal in Archive | high | 3.3.7 | 3.3.8 |
```

- Advisory の列のリンクは `database_specific.pub_display_url`。なければ ID だけを書く。ID の後に `summary` を書く
- Severity の列は `database_specific.severity`。なければ空にする
- 待機期間を無視したバージョンには、To の列でそのことを示す（例: `3.3.8 (released 1 day ago)`）

### 5.2 実行のタイミング

アドバイザリは slot（基本 §4.1）と関係なく公開されるので、アドバイザリが公開されると、slot の間でも PR が作られたり変わったりする。基本 §4.1 の「slot と slot の間に PR の内容が変わるのは、ベースや設定が変わったときだけ」の例外になる。

修正の PR を早く作りたいなら、ワークフローの `schedule` を毎日にし、設定の `schedule.cron` は週 1 回のままにする。アドバイザリがない日は、計画が同じなので何も変わらない。

## 6. 既存の仕組みとの関係

| 仕組み | 扱い |
|---|---|
| `ignore` | アドバイザリより優先する（§4） |
| 利用者がマージせずに閉じた PR | 今までどおり、同じ内容の PR は作らない。アドバイザリを直す PR でも同じ |
| `ignored_advisories` | pub と同じく、書かれたアドバイザリは無視する |
| 再生成の条件（基本 §7.2） | 変えない。アドバイザリが公開されて PR の内容が変われば、「更新内容が変わった」として再生成する |
| PR メタデータ（基本 §6.1） | 直すアドバイザリの ID を `advisories` に入れる。PR の内容が同じまま、直すアドバイザリだけが変わった場合（例: メジャー更新の PR の更新元のバージョンに、あとからアドバイザリが出た）は、コミットは作り直さず、タイトル、本文、メタデータだけを更新する |
| 待機中のバージョンの表（ジョブサマリー） | 中継サーバーで見せた修正版は、待機中に数えない |

## 7. ジョブサマリー

要修正のパッケージがあれば、表を追加する。

| Package | Locked | Advisory | Status |
|---|---|---|---|
| archive | 3.3.7 | GHSA-9v85-q87q-g4vg | Fixed in #12 |
| foo | 1.0.0 | GHSA-xxxx | No fixed version |
| bar | 2.1.0 | GHSA-yyyy | Cannot be fixed with the current constraints |

Status は次のどれか。

- `Fixed in #n`: その PR で直る
- `No fixed version`: 修正版がない（修正版が `ignore` に該当する場合を含む）
- `Cannot be fixed with the current constraints`: 修正版はあるが、どの PR でも上がらない（依存元の制約が許さない、修正版の依存が待機期間の中にある、など）

## 8. 設定

この機能は常に有効で、設定でオフにはできない。特定のアドバイザリを無視するには、pub と同じく `pubspec.yaml` の `ignored_advisories` に ID を書く。

## 9. エラー処理

- アドバイザリを取得できないときは、全体のエラーにする（何も変更せずに失敗終了する。pub.dev に到達できないときと同じ）
- 取得に失敗したパッケージを無視して続けると、次の実行で取得できたときに PR が作られ、また失敗したときに閉じられる、というように結果が揺れるため

## 10. 範囲外（この設計ではしないこと）

- 修正版の依存が待機期間の中にあるときに、その依存まで見せること。修正版だけを見せ、解決できなければジョブサマリーに出す（§7）
- 要修正の推移的依存を、依存元の直接依存のメジャー更新で直すこと。単独 PR や同時更新グループの `pub add` はロックを保つので、推移的依存は必要がなければ動かない
- 深刻度による絞り込み（`severity` が low のアドバイザリを無視する、など）
- PR に専用のラベルを付けること
- 要修正でないパッケージで、影響を受けるバージョンへの更新を避けること（§4）

## 11. 決めたこと

- アドバイザリは pub.dev の API から取る（Dependabot alerts は使わない）。利用者の準備が要らず、ベースの lockfile に対して pub と同じ基準で判定できるため
- アドバイザリを直す PR のタイトルに、固定の接頭辞 `[Security] ` を付ける
- この機能はオフにできない
- 取り下げられたアドバイザリは無視する（pub とは違う。重複として取り下げられたものが多く、たいていは同じ内容の有効なアドバイザリがある）
- 影響を受けるバージョンを隠すのは、要修正のパッケージだけにする

## 12. 確かめたこと

- pub のソース（`dart-lang/pub`、2026-10-12 のコミット 9df389a）の `lib/src/source/hosted.dart` と `lib/src/solver/report.dart` で、§2 の pub の挙動（`affected[].versions` だけを使う、`ignored_advisories` は `id` と `aliases` で照合する、`withdrawn` を見ない、`advisoriesUpdated` がなければアドバイザリを取りに行かない）を確かめた
- 2026-10-19 に pub.dev の API で、`dio`、`http`、`archive` のアドバイザリの形を確かめた。`dio` には取り下げられたアドバイザリ（GHSA-jwpw-q68h-r678、重複）が含まれていた。`webview_flutter` のバージョン一覧には `advisoriesUpdated` がなかった
- 2026-10-19 に、Dart 3.13.5 とフィクスチャー用サーバーで、§3 と §4 を試作して確かめた。中継サーバーは `RegistryProxy` の隠す判定だけを差し替え、計画と適用は今の `plan()` と `applyUnit()` をそのまま使った。待機期間は 3 日で、「新しい」は 1 日前、「古い」は 30 日前に公開した版。すべて 1.0.0 にロックした状態から始めた
