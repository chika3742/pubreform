# pubreform 基本設計

> ステータス: 実装済み（2026-10-18。v1 は未リリース）。セキュリティアドバイザリによる更新（§14.2）は 2026-10-20 に実装した。挙動を変えるときは、先にこの設計書を直す。「13. 仮決めした点」は必要に応じて更新する。実装に必要な決定は[詳細設計](detailed-design.md)に書く。

## 1. 概要

pubreform は、Dart / Flutter プロジェクトの pub 依存を更新する PR を作成・保守する GitHub Action。

設計方針:

- **状態を持たない調整型**: 実行のたびに「あるべき PR の集合」を計算し、既存 PR との差分だけを反映する。必要な情報は、設定ファイル、ベースブランチ、pub.dev、既存 PR に埋め込んだメタデータから毎回復元する。状態保存用のブランチや Issue は持たない。
- **起動イベントに依存しない**: イベントのペイロードは使わない。どのイベントで起動されても、ベースブランチの最新状態を自分で取得して同じ処理を行う。
- **依存解決は pub に任せる**: バージョン選択はすべて `dart pub` / `flutter pub` の実行結果を使い、独自の解決器は作らない。

## 2. スコープ

対象:

- リポジトリのルートにある `pubspec.yaml` / `pubspec.lock`（`pubspec.lock` がコミットされていること）
- pub.dev から取得する `dependencies` / `dev_dependencies`。推移的依存は単独では更新せず、直接依存の PR の中で一緒に上がる分だけを扱う（PR には載せない）。例外は、セキュリティアドバイザリを直す推移的依存（§14.2）
- Dart と Flutter の両方。依存に `sdk: flutter` があれば `flutter pub`、なければ `dart pub` を使う

対象外（v1）:

- path / git / sdk 依存、pub.dev 以外のホストの依存
- `dependency_overrides` に書かれたパッケージ
- Dart / Flutter SDK 自体と `environment` の更新
- pub workspace、ルート以外のディレクトリ。ルートの pubspec に `workspace:` があれば、未対応として何も変更せずに失敗終了する（将来の対応は §14.1）
- `pubspec.lock` をコミットしないプロジェクト（ライブラリなど）
- プレリリース版（更新先は安定版のみ）

前提:

- PR の作成、コミット、コメントは GitHub App のインストールトークンで行う（§11）
- Dart / Flutter SDK はワークフロー側でセットアップする。解決結果はこの SDK のバージョンに依存し、より新しい SDK を要求するバージョンは「解決不能」として扱われる
- Flutter SDK は fvm で用意する。ワークフローで `chika3742/setup-fvm` を使う（§3.2）

## 3. 全体構成

TypeScript の JavaScript Action（`runs.using: node24`）として実装する。Node 20 はランナーからの削除が告知済みのため、Node 24 を使う。

| コンポーネント | 役割 |
|---|---|
| Config | 設定ファイルの読込・検証、ハッシュ計算 |
| Clock | cron とタイムゾーンから、直近のスケジュール時刻（slot）と公開日時の締切（cutoff）を求める |
| RegistryProxy | pub.dev API を中継し、cutoff より後に公開されたバージョンを隠すローカル HTTP サーバー。セキュリティアドバイザリを直すパッケージでは、見せるバージョンを変える（§14.2） |
| Advisories | pub.dev からセキュリティアドバイザリを読み、直す対象のパッケージと修正版を決める（§14.2） |
| Planner | pub の解決結果から更新単位（= PR の単位）を決める |
| Applier | 更新単位をベースブランチの上に適用し、コミットを作る |
| Reconciler | 計画した更新単位と既存 PR を突き合わせ、作成・再生成・クローズを決める |
| Renderer | タイトル、本文、コミットメッセージ、コメントを生成する（CHANGELOG の抽出を含む） |
| GitHub | PR、コメント、ラベル、ブランチを操作する |
| Generator | 更新後のコマンド（§14.3）を Docker のコンテナで実行し、変わったファイルを集める |

### 3.1 実行フロー

1. ベースブランチ（リポジトリのデフォルトブランチ）を、作業用ディレクトリとして `RUNNER_TEMP` の下に浅く clone する（詳細 §8.1）。`GITHUB_WORKSPACE` の中に置くと、setup-fvm の post 処理が pub キャッシュのキー（`**/pubspec.lock` のハッシュ）を計算するときに作業用ディレクトリの lockfile まで含まれてキーが変わり、毎回キャッシュが保存されてしまう
2. 設定ファイルをベースブランチから読む（起動元の ref にある設定は使わない）
3. Clock で slot と cutoff を求める（§4）
4. RegistryProxy を起動する。以降の pub コマンドはすべてプロキシ経由で、作業用ディレクトリの中で実行する（§3.2）。ロック済みのパッケージのセキュリティアドバイザリを読み、直す対象のパッケージと修正版をプロキシに渡す（§14.2）
5. Planner で更新単位の集合を求める（§5）
6. 各更新単位を Applier で適用し、変更内容（pubspec の差分とバージョン変更の一覧）を得る
7. Reconciler で既存 PR（open と closed）と突き合わせ、必要な操作を実行する（§7）。PR を作る・作り直すときは、コミットを作る前に更新後のコマンドを実行する（§14.3）
8. ジョブサマリーに slot、cutoff、各 PR への操作、待機期間のために使わなかった新しいバージョン、解決できるバージョンがなく最新版に上げられない直接依存、セキュリティアドバイザリ（§14.2）、エラーを書く。エラーが 1 件でもあれば失敗終了する

### 3.2 Flutter SDK

- ワークフローで [`chika3742/setup-fvm`](https://github.com/chika3742/setup-fvm) を使い、FVM と Flutter SDK を入れる。Flutter SDK と pub のキャッシュの保存・復元も setup-fvm が行う（§10.3）
- Action は、ルートに `.fvmrc` があれば、§2 の pub コマンドの前に `fvm` を付けて実行する（`fvm flutter pub …` / `fvm dart pub …`）。fvm は実行したディレクトリの `.fvmrc` のバージョンを使う。Action は pub をベースの作業用ディレクトリの中で実行するので、使われるのはベースの `.fvmrc` のバージョンになる
- checkout した ref とベースで `.fvmrc` が違う場合は、fvm がベースのバージョンを自動でインストールしてから実行する。結果はベースのバージョンで解決したものになるが、SDK の取得に時間がかかる
- `.fvmrc` がなければ、PATH 上の `flutter` / `dart` をそのまま使う（Dart だけのプロジェクトなど。SDK は `dart-lang/setup-dart` などで用意する）
- `.fvmrc` はベースのハッシュ（§6.1）に含める。Flutter のバージョンが変わると、すべての PR を再生成する

## 4. スケジュールとリリース後の待機期間

### 4.1 スケジュールの解釈

設定の cron は「チェックを実行する時刻」ではなく、「**更新対象にするバージョンの範囲が切り替わる時刻**」として扱う。

- `slot` = 設定の cron（指定タイムゾーン）が最後に発火した時刻（現在時刻以前で直近のもの）
- `cutoff` = `slot − min_release_age_days`
- 計画では、`cutoff` 以前に公開されたバージョンだけを候補にする

この解釈で次の性質が得られる。

- 次の slot までのどの実行でも、入力（ベース、設定、pub.dev）が同じなら計画も同じになる。結果が起動のタイミングや回数に左右されない
- GitHub の schedule が遅延・欠落しても、その後の最初の実行で同じ結果が得られる。前回の実行時刻を保存する必要がない
- 新しいリリースが PR に入るのは、slot を過ぎた後の最初の実行。slot と slot の間に PR の内容が変わる（新規作成を含む）のは、ベースや設定が変わったときと導入直後だけ。新規作成する時刻は slot の直後に限らない。新規作成が起こる例:
  - 導入後の最初の実行
  - 設定の変更: `ignore` から外す、`min_release_age_days` を短くする、`schedule` を変える
  - main の変更: 古い制約で依存を追加する、lockfile で意図的にバージョンを下げる、マージ済みの bot の PR を revert する、`.fvmrc` で Flutter を上げる（新しい SDK を要求していた更新が解決できるようになる）
  - bot の PR をマージしただけでは、新しい PR はほぼ作られない（他の PR の再生成になる）
- PR に入るバージョンは、PR 作成時点で必ず `min_release_age_days` 日以上経過している
- 例外はセキュリティアドバイザリ（§14.2）。アドバイザリが公開されると、slot の間でも PR が作られたり変わったりし、アドバイザリを直す修正版は待機期間の中でも PR に入る

ワークフローの起動頻度は自由に決めてよい。slot の直後に PR が欲しい場合は、ワークフローの `schedule` を同じ cron とタイムゾーンにする（GitHub Actions の `schedule` は `timezone` を指定できる）。

### 4.2 待機期間の適用（RegistryProxy）

pub には公開日時で候補を絞る機能がない。クールダウン機能は [dart-lang/pub#4831](https://github.com/dart-lang/pub/pull/4831) でドラフトの段階で、2026-10-12 時点の master にも実装はない。そのため、pub が参照するパッケージリポジトリを差し替えて実現する。

- Action 内で `127.0.0.1` の HTTP サーバーを起動し、`PUB_HOSTED_URL` に指定して pub を実行する
- `GET /api/packages/<name>`: pub.dev の応答の `versions` から、`published` が `cutoff` より後のバージョンを除いて返す（pub は `versions` だけを読み、`latest` は使わない）。ただし、ベースの `pubspec.lock` でロックされているバージョンは必ず残す。ダウングレードを防ぐためと、Flutter SDK が要求するバージョン（下記）を隠さないためである
- `archive_url` は pub.dev の URL のまま返す。アーカイブは pub.dev から直接ダウンロードされ、`archive_sha256` で検証される
- その他のパスは pub.dev にそのまま中継する
- セキュリティアドバイザリを直すパッケージでは、影響を受けるバージョンを隠し、待機期間の中の修正版を見せる（§14.2）
- 取り下げ（retracted）されたバージョンは pub 自体が選ばないので、プロキシでは扱わない

pub は lockfile の各パッケージにホストの `url` を記録しており、`PUB_HOSTED_URL` と違う URL のエントリはロック済みとして扱わない。そのため、pub を実行する前に作業用コピーの lockfile の `url: "https://pub.dev"` をプロキシの URL（`url: "http://127.0.0.1:<port>"`。pub が書く形そのまま）に置き換え、実行後に元へ戻す。

pub はダウンロードしたパッケージを、ホストごとのディレクトリに保存する。プロキシ経由で取得したパッケージは `~/.pub-cache/hosted/localhost%58<port>/` に入り、setup-fvm が復元する `hosted/pub.dev/` とは別になる。ポートを実行ごとに変えると保存先も変わり、キャッシュが増え続けるため、プロキシのポートは固定にする。

> **検証結果**（2026-10-18。プロトタイプで確認し、その手順は結合テスト [`test/integration.test.ts`](../test/integration.test.ts) に移した）: Dart 3.13.5 の `dart pub` と、fvm 4.3.2 で入れた Flutter 3.47.7 の `fvm flutter pub` の両方で、次をすべて確認した。
> - 締切より後に公開されたバージョンは、直接依存（`http` / `dio`）でも推移的依存（`async` / `vector_math`）でも選ばれない（`pub get` / `pub upgrade` / `pub add`）
> - lockfile の URL を置き換えて実行すると、`pub get` はロックを維持する。元に戻した lockfile は、プロキシなしの pub が書くものとバイト単位で同じになる（`sha256` も同じ）
> - URL を置き換えないと、pub はロックを無視して解決し直し（`pub get` でも直接依存が上がる）、lockfile にプロキシの URL を書く
> - ロック済みのバージョンを残せば、締切より新しいバージョンがロックされていても、`pub get` / `pub upgrade` でダウングレードしない
> - pub は警告を出さない。プロキシ経由で取得したパッケージは `hosted/localhost%58<port>/` に保存される
> - pub の解決器はバージョン一覧を毎回サーバーから取得する。キャッシュ（最大 3 日）を使うのはロック済みのバージョンの情報を読むときだけで、ロック済みのバージョンは常に一覧に残すため、結果に影響しない
>
> Flutter SDK の要求: Flutter SDK のパッケージは、pub.dev のパッケージの最低バージョンを要求する（Flutter 3.47.7 の `flutter` は `meta ^1.18.3`（2026-06-04 公開）、`vector_math ^2.4.0`（2026-06-03 公開）など）。lockfile がなく、これらが締切より新しいと解決に失敗する。ベースの lockfile にはその SDK で解決したバージョンが入っているので、ロック済みのバージョンを残せば解決できる（締切を 2025-10-01 にして確認。残さないと `get` も `upgrade` も失敗する）。ただし、main で `.fvmrc` だけを上げて lockfile を更新していない場合は、新しい SDK が要求するバージョンが締切より新しいと解決に失敗する（全体エラーとしてジョブのログに出る）。
>
> pub にクールダウン機能が入ったら、この仕組みはそれに置き換える。

## 5. 更新単位の計画（Planner）

### 5.1 用語

- **直接依存**: `pubspec.yaml` の `dependencies` / `dev_dependencies` のうち、§2 の対象になるもの。`ignore` 設定に該当する範囲は、すべての解決で除外する（中継サーバーで該当バージョンを隠す。詳細 §9）
- **`c(d)`**: ベースの `pubspec.lock` での d のバージョン
- **メジャー更新**: `pubspec.yaml` の制約の範囲を超える更新。caret 制約（`^x.y.z`）なら semver の破壊的変更と一致し、`0.x` ではマイナー番号の変化もこれに当たる（`^0.3.1` = `>=0.3.1 <0.4.0`）

### 5.2 基準となる 2 つの解決

| 名前 | pubspec の一時的な書き換え | 解決方法 | 意味 |
|---|---|---|---|
| U（upgradable） | なし | `pub upgrade` | 今の制約の範囲での最新。マイナー・パッチグループの内容になる |
| R（resolvable） | すべての直接依存を `>=c(d)` に | lockfile なしで解決 | 全パッケージを最新安定版まで上げてよい場合の解決。`pub outdated` の Resolvable 列とほぼ同じ（下限を現在のバージョンにしてダウングレードを禁じる点が違う） |

一時的な書き換えは作業用コピーに対して行い、コミットには含めない。

pub の `get` / `upgrade` / `add` にはすべて `--no-example` を付ける（既定では `example/` も解決され、その lockfile も変わるため）。

### 5.3 分類

1. **マイナー・パッチグループ**: U でバージョンが変わる直接依存すべて。`pub upgrade` の結果そのものなので、同時に解決できることが保証される。推移的依存も `pub upgrade` で一緒に上がるが、PR の内容には含めない。直接依存が 1 つも変わらない（推移的依存だけが変わる）場合は PR を作らない。ただし、セキュリティアドバイザリを直す推移的依存が変わるなら作る（§14.2）。上限のない制約（`any`、`>=1.0.0` など）を持つ依存は、pub の挙動どおりメジャー更新もこのグループに入る
2. **グループ外の候補 X**: `R(d) > U(d)` となる直接依存。今の制約の範囲には収まらない更新
3. **解決不能**: 候補バージョンのうち `R(d)` より新しいもの。他のどのパッケージを最新安定版にしても選ばれないので、PR を作らない（ジョブサマリーにだけ記録する）

### 5.4 単独 PR と同時更新グループの判定

X の各 d について、一緒に上げる必要がある直接依存の集合 `S(d)` を求める。

```
S = {d}
繰り返し:
  S の要素を R のバージョンに固定し、それ以外の直接依存は >=c(e) に緩めて、
  ベースの lockfile を残したまま pub get する
  （pub はロック済みのバージョンをできるだけ維持するので、必要なものだけが動く）
  K = 元の制約の範囲から外れた、S 以外の直接依存
  K が空なら終了。空でなければ S ← S ∪ K
```

R 自体がこの条件を満たす解なので、この解決は失敗しない。

- 要素が重なる `S` 同士を 1 つにまとめ、まとめた集合で同じ反復をもう一度行って確定させる
- 要素が 1 つ: **単独 PR**
- 要素が 2 つ以上: **同時更新グループ PR**。単独で解決できるメジャー更新 B でも、他の更新 A が B を必要とするなら {A, B} の同時更新グループに入れ、B の単独 PR は作らない
- 同時更新グループに入ったパッケージでも、今の制約の範囲での更新はマイナー・パッチグループに残る。例: A の 1.2→1.4 はマイナー・パッチグループ、1.4→1.5（B 3.0 が必要）は同時更新グループに入る。マイナー・パッチグループがマージされると、同時更新グループは再生成され、内容が「A 1.4→1.5」になる

注: pub の解決器は、動かすパッケージの数を最小にするわけではない。そのため `S` は最小とは限らず、pub が選んだ結果に従う。

### 5.5 適用（Applier）

ベースの作業用ディレクトリで次を実行する。

| 更新単位 | 操作 |
|---|---|
| マイナー・パッチグループ | `pub upgrade`。`versioning: increase` なら `--tighten` を付けて下限も上げる |
| 単独 / 同時更新グループ | `pub add a:^R(a) dev:b:^R(b) …`。既存の依存の制約を書き換える。`pubspec.yaml` の書式は pub が維持する。バージョンを 1 つに固定した制約（`a: 1.2.3`）は、固定のまま `a:R(a)` で上げる |

変更されるのは `pubspec.yaml` と `pubspec.lock` だけ。PR の内容（どの直接依存を何から何へ）は、計画値ではなく適用後の lockfile の差分から求める。推移的依存の変化は、どの更新単位でも lockfile にそのまま入れ、PR の内容（本文、表、コメント）では触れない。

## 6. PR の種類と識別

| 種類 | ブランチ | タイトル |
|---|---|---|
| 単独 | `pubreform/single/<package>` | `Update <package> from <前> to <後>` |
| マイナー・パッチグループ | `pubreform/minor-and-patch` | `Update minor and patch (<N> packages)` |
| 同時更新グループ | `pubreform/group/<作成時の先頭パッケージ名>` | `Update <package> to <後>, <package 2> to <後>, ...` |

- セキュリティアドバイザリを直す PR は、タイトルの前に `[Security] ` を付ける（§14.2）
- N はバージョンが変わる直接依存（`dependencies` / `dev_dependencies`）の数（セキュリティアドバイザリを直す推移的依存も数える。§14.2）。N = 1 のときは、グループでもタイトルを単独 PR と同じ `Update <package> from <前> to <後>` にし、コミットメッセージもタイトルだけにする
- 同時更新グループのタイトルには、グループのメンバー（同時に上げる必要のあるパッケージ）をパッケージ名の順に並べる。メンバー以外で動いた直接依存は、単独 PR と同じく本文の表にだけ載せる
- コミットはベースの最新コミットの上に 1 つだけ作る。コミットメッセージの 1 行目はタイトルと同じ。グループの場合は本文に、更新した直接依存の表を入れる

```
Update minor and patch (2 packages)

| Package | From | To | Type |
|---|---|---|---|
| http | 1.5.0 | 1.6.0 | direct |
| lints | 6.0.0 | 6.1.0 | dev |
```

### 6.1 PR メタデータ

本文の末尾に HTML コメントで埋め込む。

```html
<!-- pubreform:meta {"v":1,"kind":"group","packages":{"http":["1.5.0","1.6.0"]},"baseHash":"…","configHash":"…","commit":"…"} -->
```

| キー | 用途 |
|---|---|
| `kind`, `packages` | 計画との突き合わせ、内容の変更の検出、クローズ済み PR の再作成の抑止 |
| `baseHash` | 生成時のベースの `pubspec.yaml`、`pubspec.lock`、`.fvmrc` のハッシュ。ベースの更新と Flutter のバージョン変更を検出する |
| `configHash` | 設定の変更を検出する |
| `advisories` | 直すセキュリティアドバイザリの ID。直すアドバイザリだけが変わったことを検出する（§14.2） |
| `commit` | 生成したコミットの SHA。PR の head がこれとも、再生成の直前の head（`previous`）とも違えば、人手のコミットがある（詳細 §14.3） |

PR の識別にはブランチ名の接頭辞、作成者、メタデータを使い、ラベルは使わない（ラベルは利用者が付け外しするため）。作成者が bot の PR だけを pubreform の PR とみなす。人が `pubreform/` で始まるブランチから作った PR を、再生成で上書きしたり、不要として閉じてブランチを消したりしないため。

## 7. 調整（Reconciler）

### 7.1 計画と既存 PR の突き合わせ

- 単独 PR とマイナー・パッチグループは、種類とブランチ名で対応させる
- 同時更新グループは、パッケージの集合が最も多く重なる既存のグループ PR と 1 対 1 で対応させる。メンバーが変わっても同じブランチを使い続ける

### 7.2 各 PR への操作

| 状況 | 操作 |
|---|---|
| 計画にあり、PR がない | PR を作成し、設定のラベルを付ける。ただし、同じ種類で同じ内容（パッケージと更新後のバージョン）の、利用者がマージせずにクローズした PR があれば作らない（直近 100 件を確認。pubreform 自身が閉じた PR は対象外。詳細 §14.3） |
| 計画になく、PR がある | 理由をコメントしてクローズし、ブランチを削除する（例: ベースで更新済み、`ignore` に追加された、同時更新グループに統合された）。ただし、PR のパッケージの計画に失敗した場合は閉じない（詳細 §14.3） |
| 両方ある | 次の条件のどれかを満たせば再生成する |

再生成の条件:

| 条件 | 判定方法 |
|---|---|
| 本文のチェックボックスがチェックされた | 本文中のマーカー付きチェックボックスが `[x]` |
| ベースとコンフリクトしている | PR の `mergeable_state` が `dirty`。`mergeable` が未計算なら今回は判定しない |
| 更新内容が変わった | 適用結果の `packages` がメタデータと違う |
| ベースの `pubspec.yaml` / `pubspec.lock`（と `.fvmrc`）が更新された | ベースのハッシュがメタデータの `baseHash` と違う |
| 設定が変わった | 設定のハッシュがメタデータの `configHash` と違う |

PR が変更するのは pubspec の 2 ファイルだけなので、コンフリクトはほぼ `baseHash` の比較で検出できる。`mergeable_state` は念のために見る。

再生成の手順:

1. ベースの最新コミットを親にして、コミットを作り直す（1 コミットのまま。amend と同じ結果になる）
2. 同じブランチを新しいコミットへ強制的に更新する（force push に当たる。方法は §11）。直前にブランチの head が想定どおりかを確かめ、違えば更新しない
3. タイトル、本文、メタデータを更新し、チェックボックスを未チェックに戻す
4. **更新内容が変わった場合だけ**、変更点をコメントする（追加・削除・更新後のバージョンの変更を表にする）。更新前のバージョンだけが変わった場合（例: マイナー・パッチグループのマージで From が変わる）や、推移的依存だけが変わった場合は、内容の変更に含めない

どの再生成の条件にも当てはまらず、直すセキュリティアドバイザリだけが変わった場合は、コミットは作り直さず、タイトル、本文、メタデータだけを更新する（§14.2）。

人手のコミットがある PR（head がメタデータの `commit` とも `previous` とも違う）は自動では再生成しない。最初に検出したときに 1 回だけその旨をコメントする。チェックボックスがチェックされた場合は、人手のコミットを破棄して再生成する。

### 7.3 同時実行

- ワークフローの `concurrency` で実行を直列にする（§10.3）
- ブランチを更新する直前に head を確認し、想定と違えば更新せずにエラーとして扱う（§9）。確認してから更新するまでの間に入った push は検出できないが、直列化していれば通常は起きない

## 8. PR 本文

本文とコメントの文言は、タイトルに合わせて英語にする。

````markdown
Updates the following packages.

| Package | From | To | Type |
|---|---|---|---|
| [http](https://pub.dev/packages/http) | 1.5.0 | 1.6.0 | direct |

### http 1.5.0 → 1.6.0

[pub.dev](https://pub.dev/packages/http/versions/1.6.0) · [Source](https://github.com/dart-lang/http/tree/master/pkgs/http)

<details>
<summary>Changelog</summary>

## 1.6.0
...

</details>

---

- [ ] Rebase this PR <!-- pubreform:rebase -->

<!-- pubreform:meta {...} -->
````

- 本文には直接依存だけを載せる。推移的依存は表にも載せない。例外は、セキュリティアドバイザリを直す推移的依存（§14.2）
- セキュリティアドバイザリを直す PR では、本文の先頭にアドバイザリの表を置く（§14.2）
- **ソースへのリンク**: 更新後のバージョンの pubspec の `repository`。なければ `homepage`。どちらもなければ省略する
- **更新履歴**: pub がキャッシュに展開した、更新後のバージョンの `CHANGELOG.md` から（詳細 §12.3）、「更新前 < v ≤ 更新後」に当たるバージョン見出しの節を抜き出す。見出しにバージョン文字列を含む行（`## 1.6.0`、`## [1.6.0] - 2025-11-10`、`# v1.6.0` など）を見出しとみなす
- 抜き出せない場合や取得できない場合は、`https://pub.dev/packages/<package>/changelog` へのリンクだけを載せる
- 本文の上限（65,536 文字）を超える場合は、パッケージごとの更新履歴を切り詰めてリンクを付ける

## 9. エラー処理

| 発生箇所 | 扱い |
|---|---|
| 既存 PR がある更新単位の処理中（適用、ブランチの更新、PR 操作） | その PR にエラーログをコメントする。ブランチは変更しない。他の更新単位の処理は続ける |
| まだ PR がない更新単位の処理中 | ジョブのログに出す |
| 全体（設定の誤り、pub.dev に到達できない、セキュリティアドバイザリを取得できない（§14.2）、SDK がない） | 何も変更せずに失敗終了する |
| 更新履歴やソースリンクの取得 | エラーにしない。本文に取得できなかった旨と pub.dev へのリンクを載せる |

- 同じエラーを毎回コメントしないように、エラーログのハッシュをコメント内のマーカーに入れ、その PR の直近のエラーコメントと同じハッシュなら投稿しない
- コメントするログは末尾の一定量（例: 200 行）に切り詰める。API で投稿する文字列には Actions のシークレットのマスクが効かないので、入力のトークンと URL に含まれる認証情報を伏せ字にする
- エラーが 1 件でもあれば、最後に Action を失敗終了させる（ワークフローの失敗通知で気づけるようにする）

## 10. 設定

### 10.1 Action の入力

| 入力 | 既定値 | 説明 |
|---|---|---|
| `token` | （必須） | GitHub App のインストールトークン（§11） |
| `config` | `.github/pubreform.yaml` | 設定ファイルのパス。ベースブランチから読む |

### 10.2 設定ファイル

```yaml
# $schema: https://raw.githubusercontent.com/chika3742/pubreform/v1/pubreform.schema.json
schedule:
  cron: "0 9 * * 1"         # 必須
  timezone: Asia/Tokyo      # IANA のタイムゾーン名。既定は UTC
min_release_age_days: 3     # 既定は 0
labels: [dependencies]      # PR に付けるラベル
versioning: increase        # increase | lockfile-only（マイナー・パッチグループで pubspec の下限を上げるか）
ignore:
  - name: some_package      # 名前だけなら、すべての更新を対象外にする
  - name: other_package
    versions: ">=3.0.0"     # この範囲のバージョンへの更新を対象外にする
```

設定ファイルの置き場所は `.github/pubreform.yaml`（入力 `config` で変えられる）。先頭の行で JSON スキーマ（[`pubreform.schema.json`](../pubreform.schema.json)）を指定すると、エディタで補完と検証が効く（詳細 §4.2）。

`versioning` と `ignore` は要件にはない追加項目。不要なら削除する。更新後のコマンド（`post_update`）の設定は §14.3。

### 10.3 ワークフロー例

```yaml
name: pubreform

on:
  schedule:
    - cron: "0 9 * * 1"
      timezone: Asia/Tokyo
  push:
    branches: [main]
    paths: [pubspec.yaml, pubspec.lock, .fvmrc, .github/pubreform.yaml]
  pull_request:
    types: [edited]          # チェックボックスへの即時対応
  workflow_dispatch:

concurrency:
  group: pubreform
  cancel-in-progress: false

jobs:
  pubreform:
    # pull_request は bot の PR だけ。App 自身による本文の更新では起動しない
    if: >-
      github.event_name != 'pull_request' ||
      (startsWith(github.head_ref, 'pubreform/') && github.event.sender.type != 'Bot')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/create-github-app-token@v3
        id: app-token
        with:
          client-id: ${{ vars.PUBREFORM_CLIENT_ID }}
          private-key: ${{ secrets.PUBREFORM_PRIVATE_KEY }}
      - uses: actions/checkout@v7
      - uses: chika3742/setup-fvm@v3        # Dart だけなら dart-lang/setup-dart@v1
      - uses: chika3742/pubreform@v1
        with:
          token: ${{ steps.app-token.outputs.token }}
```

## 11. トークンと権限

- PR の作成、コミット、コメント、ラベル付けは、`token` に渡した GitHub App のインストールトークンで行う。`GITHUB_TOKEN` は使わない（`GITHUB_TOKEN` で作った PR では、`pull_request` で起動する CI が承認待ちになるため）
- App に必要な権限（Repository permissions）: Contents（Read and write）、Pull requests（Read and write）。コメントとラベルの API は Pull requests の権限で使える
- コミットは git の push ではなく、GitHub API（blob → tree → commit → ref の更新）で作る。App として認証し author / committer を指定しなければ、コミットは App の bot ユーザーの名義になり、GitHub の署名で Verified と表示される。変更するのは 2 ファイルだけなので、API の呼び出しは数回で済む
- ref を更新する REST API には「head が想定どおりなら更新する」という条件を付けられないため、§7.3 のとおり直前に確認する
- App による push や PR の作成では、通常どおり CI などの他のワークフローが起動する。App 自身が本文を更新したときも `pull_request: edited` で起動するので、ワークフロー側で除外する（§10.3）

## 13. 仮決めした点

次の点は仮の方針で設計に反映している。必要なら変更する。

- マイナー・パッチグループでも pubspec の下限を上げる（`versioning: increase`、`pub upgrade --tighten`）（§5.5）
- 人手のコミットがある PR は自動で再生成しない（§7.2）
- 利用者がマージせずにクローズした PR と同じ内容の PR は再作成しない（§7.2）
- プレリリース版は対象外
- 本文とコメントは英語
- コミットは API で作る（Verified になり、git の認証設定も要らない。代わりに、head の確認から ref の更新までの間に入った push は検出できない）（§11）

## 14. 将来の拡張

### 14.1 pub workspace

v1 はルートの 1 パッケージだけを扱う。pub workspace では、lockfile はルートに 1 つで、制約は各メンバーの `pubspec.yaml` にある。同じパッケージを複数のメンバーが別々の制約で宣言することもある。後から対応しやすいように、v1 から次の形で実装しておく。

- 「`pubspec.yaml` の一覧」と「lockfile」を分けて扱う。v1 では一覧はルートの 1 つだけ
- 直接依存は「パッケージ名 → それを宣言している `pubspec.yaml` の一覧」で持つ。制約の書き換え（R の計算、`pub add`）は、宣言しているすべての `pubspec.yaml` に対して行う
- `baseHash` は、一覧のすべての `pubspec.yaml`、lockfile、`.fvmrc` から計算する

PR の単位とブランチ名は lockfile ごとに決まるので、workspace に対応しても変えなくてよい（workspace 全体で 1 組の PR になる）。lockfile が複数ある構成（独立したプロジェクトが並ぶリポジトリ）に広げる場合は、ブランチ名にディレクトリを入れる（例: `pubreform/<dir>/minor-and-patch`）。

### 14.2 セキュリティアドバイザリ

> 実装済み（2026-10-20）。Dart 3.13.5 で、単体テスト、ローカル E2E（詳細 §17.1 の場面 12、13）、本物の `dart pub` と pub.dev での確認（詳細 §20.5）を行った。本物の GitHub での表示は確かめていない。実装のための決定は[詳細設計](detailed-design.md) §20 などに書く。

ベースの `pubspec.lock` でロックしているバージョンに、セキュリティアドバイザリ（以下、アドバイザリ）がある場合、それを直すバージョンへの更新を、待機期間（`min_release_age_days`）が過ぎていなくても PR にする。

待機期間は、公開直後のバージョン（壊れたリリースや乗っ取られたリリース）を避けるためのものである。脆弱性の修正は早く入れたいので、この 2 つを両立させるために、待機期間を無視するのは「アドバイザリを直すのに必要な最小限のバージョン」に限る。

#### pub と pub.dev のアドバイザリ

- pub.dev は、GitHub Advisory Database のうち Pub のエコシステムのものを、OSV 形式で返す
  - `GET /api/packages/<name>`（バージョン一覧）に `advisoriesUpdated` があれば、そのパッケージにアドバイザリがある。なければない
  - `GET /api/packages/<name>/advisories` が、`advisories`（OSV の配列）と `advisoriesUpdated` を返す
- 影響を受けるバージョンは、`affected[]` のうち `package.name` がそのパッケージで `package.ecosystem` が `Pub` の要素の、`versions` にすべて並ぶ。pub もこのフィールドだけを使い、`ranges` は読まない
- pub は、利用者がルートの `pubspec.yaml` の `ignored_advisories` に書いた ID（アドバイザリの `id` か `aliases` のどれか）のアドバイザリを報告しない
- 取り下げられたアドバイザリ（`withdrawn` がある）も、pub.dev は返す。pub は `withdrawn` を見ていない

アドバイザリは pub.dev の API から取る。Dependabot alerts は使わない。利用者の準備（Dependabot alerts の有効化と App の権限）が要らず、ベースの lockfile に対して pub と同じ基準で判定できるため。

#### 用語

- **有効なアドバイザリ**: `withdrawn` がなく、ベースの `pubspec.yaml` の `ignored_advisories` に `id` も `aliases` も書かれていないアドバイザリ。取り下げられたものを無視するのは pub と違う。重複として取り下げられたものが多く、たいていは同じ内容の有効なアドバイザリがあるため
- **影響を受けるバージョン**: 有効なアドバイザリのどれかの `affected[].versions` に入っているバージョン
- **要修正のパッケージ**: ベースの lockfile でロックしているバージョン `c(p)` が影響を受けるバージョンである、pub.dev のパッケージ p。直接依存か推移的依存かは問わない
- **修正版 `f(p)`**: p のバージョンのうち、`c(p)` より新しい安定版で、取り下げ（retracted）されておらず、影響を受けず、`ignore` に該当しないもので、最も古いバージョン（バージョンの順序で最も小さいもの。公開日時の順ではない）

#### 中継サーバーで見せるバージョン

待機期間と同じく、中継サーバー（§4.2）で pub に見せるバージョンを変える。pub の解決はそのまま使う。

要修正のパッケージ p について、次の 2 つを行う。ほかのパッケージは今までどおり扱う。

1. **影響を受けるバージョンを隠す**: p の影響を受けるバージョンを隠す。ただし、ロック済みのバージョン `c(p)` は今までどおり残す
2. **修正版を見せる**: `f(p)` が待機期間の中にあれば、`f(p)` だけを見せる。`f(p)` が依存するパッケージには、今までどおり待機期間を適用する

`ignore` の設定は、これより優先する。`ignore` に該当するバージョンは、修正版に選ばず、見せない。修正版は `ignore` に該当しないものから選ぶので、最も古い修正版が `ignore` に該当しても、次に古い修正版を見せる。

1 は、2 を正しく働かせるために要る。たとえば `c(p)` = 1.2.3 が影響を受け、1.3.0（待機期間の外、影響を受ける）と 1.2.4（待機期間の中、修正版）がある場合、1 がないと pub は今の制約の中で最も新しい 1.3.0 を選び、脆弱性は直らない。

要修正でないパッケージでは、影響を受けるバージョンを隠さない。隠すと、影響を受けるバージョンを要求する依存がある場合に、今まで作れていた PR が作れなくなるため。そのため、要修正でないパッケージの更新先が、影響を受けるバージョンになることはある（そのバージョンが lockfile に入ると、次の実行からは要修正のパッケージとして扱う）。

`f(p)` を「最も新しい修正版」ではなく「最も古い修正版」にするのは、待機期間を無視するバージョンを 1 つにし、公開されてからの時間がなるべく長いものにするためである。修正のバックポート（1.2.4 と 1.3.1 のように、古い系列にも修正が出る）があっても、今の制約に収まる修正版が選ばれる。

#### 計画と PR への反映

中継サーバーで見せるバージョンが変わるだけなので、計画（§5）の手順は変えない。

- **要修正の直接依存**: 修正版が今の制約に収まれば、U に入りマイナー・パッチグループに入る。収まらなければ、メジャー更新として単独 PR か同時更新グループに入る
- **要修正の推移的依存**: マイナー・パッチグループの `pub upgrade` で、依存元の制約が許せば修正版に上がる
  - 直接依存が 1 つも変わらなくても、要修正の推移的依存が修正版に変わるなら、マイナー・パッチグループを作る（§5.3 の例外）
  - 依存元の制約が修正版を許さないときは、PR では直さず、ジョブサマリーに出す

PR がアドバイザリを直すかどうかは、計画ではなく、適用した後の lockfile の差分で判定する（§5.5 と同じ）。要修正のパッケージが、影響を受けないバージョンに変わっていれば、その PR はアドバイザリを直す。

PR の文面:

- アドバイザリを直す PR のタイトルには、接頭辞 `[Security] ` を付ける（例: `[Security] Update archive from 3.3.7 to 3.3.8`）。接頭辞は固定で、設定では変えられない。コミットメッセージの 1 行目もタイトルと同じにする（§6）
- 本文とコミットメッセージの表に、直した推移的依存も `transitive` の種類で載せる（ほかの推移的依存は今までどおり載せない）。マイナー・パッチグループの N（§6）にも数える
- 本文の先頭に、直すアドバイザリの表を置く。Advisory の列のリンクは `database_specific.pub_display_url`（なければ ID だけ）で、ID の後に `summary` を書く。Severity の列は `database_specific.severity`。待機期間を無視したバージョンには、To の列に公開日を書く

```markdown
Fixes the following security advisories.

| Package | Advisory | Severity | From | To |
|---|---|---|---|---|
| [archive](https://pub.dev/packages/archive) | [GHSA-9v85-q87q-g4vg](https://github.com/advisories/GHSA-9v85-q87q-g4vg) Path traversal in Archive | high | 3.3.7 | 3.3.8 (released 2026-10-18) |

Versions with a release date are used before `min_release_age_days` has passed, to fix the advisory.
```

#### 既存の仕組みとの関係

| 仕組み | 扱い |
|---|---|
| slot（§4.1） | アドバイザリは slot と関係なく公開されるので、公開されると slot の間でも PR が作られたり変わったりする。修正の PR を早く作りたいなら、ワークフローの `schedule` を毎日にし、設定の `schedule.cron` は週 1 回のままにする（アドバイザリがない日は、計画が同じなので何も変わらない） |
| `ignore` | アドバイザリより優先する |
| `ignored_advisories` | pub と同じく、書かれたアドバイザリは無視する。特定のアドバイザリを無視する方法はこれだけで、この機能そのものはオフにできない |
| 利用者がマージせずに閉じた PR（§7.2） | 今までどおり、同じ内容の PR は作らない。アドバイザリを直す PR でも同じ |
| 再生成の条件（§7.2） | 変えない。アドバイザリが公開されて PR の内容が変われば、「更新内容が変わった」として再生成する |
| PR メタデータ（§6.1） | 直すアドバイザリの ID を `advisories` に入れる。PR の内容が同じまま、直すアドバイザリだけが変わった場合（例: メジャー更新の PR の更新元のバージョンに、あとからアドバイザリが出た）は、コミットは作り直さず、タイトル、本文、メタデータだけを更新する |
| 待機中のバージョンの表（ジョブサマリー） | 中継サーバーで見せた修正版は、待機中に数えない |

#### ジョブサマリー

要修正のパッケージがあれば、表を追加する。

| Package | Locked | Advisories | Status |
|---|---|---|---|
| archive | 3.3.7 | GHSA-9v85-q87q-g4vg | Fixed in #12 |
| foo | 1.0.0 | GHSA-xxxx | No fixed version |
| bar | 2.1.0 | GHSA-yyyy | Cannot be fixed with the current constraints |

Status は次のどれか。

- `Fixed in #n`: その PR で直る
- `Not updated in #n (manual commits)`: その PR で直るが、人手のコミットがあるので更新しない
- `Closed in #n`: 直す PR は、利用者がマージせずに閉じた PR と同じ内容なので作らない
- `Error`: 直す PR の処理がエラーになった。または、そのパッケージの計画か適用に失敗した（推移的依存では、マイナー・パッチグループの適用に失敗した）
- `No fixed version`: `ignore` に該当しない修正版がない
- `Cannot be fixed with the current constraints`: 修正版はあるが、どの PR でも上がらない（依存元の制約が許さない、修正版の依存が待機期間の中にある、など）

#### エラー処理

アドバイザリを取得できないときは、全体のエラーにする（何も変更せずに失敗終了する。pub.dev に到達できないときと同じ）。取得に失敗したパッケージを無視して続けると、次の実行で取得できたときに PR が作られ、また失敗したときに閉じられる、というように結果が揺れるため。

#### 範囲外

- 修正版の依存が待機期間の中にあるときに、その依存まで見せること。修正版だけを見せ、解決できなければジョブサマリーに出す
- 要修正の推移的依存を、依存元の直接依存のメジャー更新で直すこと。単独 PR や同時更新グループの `pub add` はロックを保つので、推移的依存は必要がなければ動かない
- 深刻度による絞り込み（`severity` が low のアドバイザリを無視する、など）
- PR に専用のラベルを付けること
- 要修正でないパッケージで、影響を受けるバージョンへの更新を避けること

#### 確かめたこと

- pub のソース（`dart-lang/pub`、2026-10-12 のコミット 9df389a）の `lib/src/source/hosted.dart` と `lib/src/solver/report.dart` で、上の pub の挙動（`affected[].versions` だけを使う、`ignored_advisories` は `id` と `aliases` で照合する、`withdrawn` を見ない、`advisoriesUpdated` がなければアドバイザリを取りに行かない）を確かめた

### 14.3 更新後のコマンド

> 実装済み（2026-10-19）。コマンドは Docker のコンテナで実行する。Docker が使える Linux のランナーで使える。実装のための決定は[詳細設計](detailed-design.md) §19 に書く。

依存を上げたあとに、生成コード（build_runner など）を作り直したいことがある。利用者のワークフローで後からコミットを足すと、pubreform は人のコミットとみなしてその PR を更新しなくなり（§7.2）、作り直すときの強制 push で足したコミットも消える。そこで、pubreform がコミットを作る前に、設定したコマンドを実行し、変わったファイルも同じコミットに入れる。Renovate の `postUpgradeTasks` と同じ考え方。

#### 設定

```yaml
post_update:
  - run: dart run build_runner build
  - run: ./tool/generate_api.sh
    network: true          # 既定は false
    env: [API_SPEC_URL]    # 渡す環境変数を追加する
```

- `run`: シェルで実行するコマンド。上から順に実行する
- `network`: ネットワークを使えるようにするか。既定は `false`
- `env`: 既定の環境変数（後述）に加えて渡す変数の名前。値はワークフローの環境から取る
- 設定の変更なので、`post_update` を変えるとすべての PR が作り直される（§7.2）

#### いつ実行するか

PR を作るときと作り直すとき（§7.2）に、その更新単位のコミットを作る前に実行する。PR 1 つにつき 1 回で、グループ PR でも、含まれるパッケージをまとめて上げたあとの状態で 1 回だけ実行する（パッケージごとには実行しない）。`post_update` に複数のコマンドがあれば、上から順に 1 回ずつ実行する。

- 実行のたびにすべての更新単位を適用し直すが（§7）、そこではコマンドを実行しない。作り直すかどうかはパッケージとバージョン、`baseHash`、`configHash` で決まり、生成結果を使わないため。変化のない PR のために毎回生成を走らせずに済む
- 生成に関係するパッケージが変わったときだけ実行する方式は採らない。生成結果は推移的依存（`source_gen`、`analyzer` など）にも左右され、関係するパッケージを利用者が漏れなく挙げるのは難しいため。実行時間が問題になれば、条件を付けられるようにする

#### 安全な実行

コード生成は依存パッケージのコード（build_runner の builder など）を実行する。新しいバージョンのパッケージに悪意のあるコードがあれば、pubreform の権限で動いてしまう。守りたいのは App のトークンで、これを読めればリポジトリへの書き込みができる。

環境変数を絞るだけでは足りない。同じユーザーで動くプロセスは、ほかのプロセスの環境変数を `/proc/<pid>/environ` から読める（2026-10-19 に、環境変数をすべて外して起動したプロセスから、同じユーザーの別プロセスの値を読めることを確認）。pubreform の入力 `INPUT_TOKEN`、ランナーが持つ Actions 用のトークン、`actions/checkout` がディスクに残す認証情報（`RUNNER_TEMP` の下。ほかのユーザーにも読める権限と考えられる）が、どれも読めてしまう。

そこで、コマンドは Docker のコンテナの中で実行する。イメージはレジストリから取得せず、実行のたびにランナーのファイル（ディレクトリの骨組みと `/etc` の一部）から作る。Docker Hub などの取得回数の制限を避けるためで、ランナーの `/usr` を重ねるので、イメージの中身はそれだけで足りる（詳細 §19.1）。

| 対策 | 防げること |
|---|---|
| コンテナに、生成用のディレクトリ、SDK、pub のキャッシュ、ランナーの `/usr` だけをマウントする。生成用以外は読み取り専用 | ランナーのファイル（認証情報）を読まれること。SDK と pub のキャッシュを書き換えられること（書き換えられると、あとで pubreform が実行する pub が改ざんされる） |
| コンテナの中からは、ランナーのプロセスが見えない（Docker が PID の名前空間を分ける） | ほかのプロセスの環境変数からトークンを読まれること |
| 環境変数を絞る。既定は `PATH`、`HOME`、`PUB_CACHE`、`LANG` など（詳細 §19.5）、それに `env` で指定したものだけ | 渡した環境変数から漏れること |
| `network: false` ならネットワークなしで実行する（`--network none`） | リポジトリの中身などを外部へ送られること |

トークンは、ネットワークの有無に関係なく、コンテナに入れないことで守る。ネットワークを切って守れるのは、リポジトリの中身（非公開のソースなど）を送られることだけである。更新の PR に対しては、利用者の CI が同じ新しいコードをネットワークありで実行するので、ネットワークを切って減らせる危険は限られる。それでも、よく使う生成はネットワークなしで動くので、既定では切る。

前の方式（別のユーザーで、`sudo` と `unshare` を使って実行する）をやめたのは、隔離を自分で組み合わせると漏れを確かめるのが難しく、SDK や pub のキャッシュがランナーのホームの下にあると、読ませるためにホームをたどる権限を与える必要があり、その下の認証情報まで読めるおそれがあったため。

コンテナでは、ランナーの `/usr` を読み取り専用で重ねる。利用者がワークフローで入れたツール（`apt-get install` したもの）を、そのまま使えるようにするため。ホームの下にあるツールは使えない。

Docker が使える Linux のランナーだけで動かす。それ以外では、`post_update` があれば何もせずに失敗終了する。

Flutter のプロジェクトでも使えるが、コンテナの中で使えるのは SDK に同梱の Dart だけで、`flutter` コマンド（`flutter gen-l10n` など）は使えない。`flutter` は起動のたびに SDK の中（`bin/cache`）に書き込むが、SDK は読み取り専用でマウントするため（詳細 §19.9）。build_runner は同梱の Dart で動く（コンテナの中で確認済み。Pigeon（`dart run pigeon`）は未確認）。`.fvmrc` のある Dart だけのプロジェクトも、fvm が入れた Flutter SDK の Dart を使うので、同じ扱いにする。

#### コミットに入れるもの

コマンドのあとに変わったファイル（変更、追加、削除）を、すべて `pubspec.yaml`、`pubspec.lock` と同じコミットに入れる。`.gitignore` で除外されたものは入れない。コマンドは更新単位ごとに新しく作ったディレクトリ（ベースの状態）で実行するので、前の更新単位の結果は残らない。

#### 決めたこと・確かめたこと

- コミットに入れるファイルは、変わったものすべてにする（パターンで絞る設定は作らない）
- コマンドが失敗したら、その更新単位のエラーにする（PR を作らない。PR があればエラーをコメントし、PR は変えない。ジョブは失敗する）。生成なしで PR を作ると、生成コードが古いまま CI で落ちる PR になるため
- `dart run` は、中継サーバーの URL の lockfile で `pub get --offline` を済ませておけば、ネットワークなしでも暗黙の `pub get` を始めない（詳細 §19.8）
- コンテナの中で、読み取り専用の Dart SDK と pub のキャッシュで `dart run` が動き、ランナーのプロセスと環境変数が見えず、ネットワークに接続できない（詳細 §19.8）。Flutter SDK では `flutter` が動かない（上記）
- GitHub のランナーで、`docker` が使え、ランナーのファイルから作ったイメージで動き、コンテナから認証情報とトークンが読めないことを、pubreform-e2e（詳細 §17.2、[run #6](https://github.com/chika3742/pubreform-e2e/actions/runs/39206665275)）で確かめた
- main の生成コードがすでに古いと、作り直した差分がすべての PR に混ざる。README に、先に main で生成コードを最新にしておくよう書く
